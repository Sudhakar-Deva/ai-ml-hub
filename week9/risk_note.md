**Who wrote it:** the Claims Platform team (vendored `vendor/claims_system_mcp/` v0.4.1, which isn't our code or review), and it reports the SDK's version (1.30.0) as its own in `serverInfo`, so we can't tell from the wire which build we're running.
**What it can reach:** every claim in its store. Both tools take any claim number and return the full status record or the full adjuster note history (policy numbers, amounts, adjuster ids, free-text site-visit notes). It runs as a child process with our filesystem permissions, gets only `CLAIMS_API_TOKEN` and its own config from our env (the SDK's minimal environment, so `LLM_API_KEY` isn't passed), and nothing stops it from opening network connections.
**What it logs:** one JSON line per call to `CLAIMS_SYSTEM_LOG` (ts, first 6 characters of the token, tool, claim number, found). It doesn't log note text, but the log is a full map of which claims the assistant opened, and it sits in our repo tree (`week9/claims_system_access.log`).
**What a stolen token could do:** this build only checks that the token is non-empty, with no per-claim, per-tool or read-only scoping. Anyone holding a token (or able to set the env var) can read the adjuster notes of every open claim, and the only audit trail is the 6-character prefix in that log.
**Ship or don't:** don't ship to production as-is. Ship to Monday's triage only with a token scoped to read-only `get_claim_status` plus `get_adjuster_notes` on the triage queue's claims, the log moved out of the repo, and the vendor's own version reported in `serverInfo`.
